# Cedar Valley 与 Blackridge 地图调整

两张地图沿用 v10 的三天、10 点共享资源、每天 5 点和最多两队。保留原有地点和连线，通过提高部分路段的通行消耗、调整幸存者分布，让同一深度的目的地也可能需要不同的投入。以下为教师审阅用数据，含地图真值。

## 玩家多了一项什么判断

**Cedar Valley。** 西林 W3 和 W4 在同一个岔口后面，深度相同。派 3 点到 W3，沿途可救 3 人。派 4 点到 W4，可救 4 人，但当天只剩 1 点能派往其他方向。如果首日只派这一队，两个开局在后续完美决策下分别最多救 13 和 14 人。作为对照，只交换 W3、W4 两处的隐藏人数，保持地图、路费和公开报告完全相同，最好的开局就从 W4 换成 W3。观察哪一处人多，确实有可能改变值得采取的行动。北岭 N4 也需要 4 点，河路尽头 R5 则要用满一天的 5 点。

**Blackridge。** 湖区的 Weather Station 和 Lakeside Camp 同样深。初报只给整个湖区的估计。Weather Station 需要 3 点，沿途救 5 人。Lakeside Camp 需要 4 点，沿途救 3 人。去 Weather Station 后，剩下的 2 点足以另派一队到 Creek Shelter，领取次日的补给。两种单队开局都仍有机会达到 18 人，但当天的救援量和第二队的选择不同。北坡的 Summit Cabin 需要 5 点，投入整天去一次远端还是拆成两队，是另一种取舍。

公开简报提供路线概况并标明补给所在地点。浏览未探索地点时，地图说明不列出精确通行消耗或现场人数。未来接入望远镜时，玩家确认选点后可以读取该点本身的通行消耗；看到多少人由画面和玩家观察决定。本次改动覆盖地图、结算和验证。实际玩家用望远镜后是否更愿意讨论，需在功能接入后试玩。

## 验证结果

| 指标 | Cedar Valley | Blackridge |
|---|---:|---:|
| 教师 v10 验收项 | 11/11 | 11/11 |
| 满信息最优救援数 | 14/21（66.7%） | 18/26（69.2%） |
| 只允许每天一队的最优 | 13 | 16 |
| 每天资源上限降为 4 的最优 | 13 | 16 |
| 最贵的完整路线 | 5 点 | 5 点 |
| 近优首日方案数（终局距最优最多 1 人） | 227 | 362 |
| 次日保持最优的方案（按教师验证器口径） | 131/1281（10.2%） | 201/1621（12.4%） |
| 第三天保持最优的方案（验证器选取的路径） | 49 | 147 |
| 单处人数或通行费增减 1 后仍通过全部 11 项 | 40/47（85.1%） | 45/51（88.2%） |
| 取消补给后，最优救援数减少 | 1 | 2 |
| 项目内兼顾补给和救援的公开信息策略 | 12/14 | 15/18 |

后期方案数可能包含救援结果相同的不同派法。满信息最优展示的是地图上限；在真实试玩中，玩家只能依据已经获得的信息行动。

**情报时机另做了对照。** 教师原验证器的策略会在首日读取修正值，并用隐藏人数判断是否继续搜某条路线。原验证器按原样运行以保留可比性。另外测试了一条只按当日公开报数选择尚未访问分支、向最深处派一队的规则。两次运行的首日行动相同，只在第二天开始决定是否采用新报告。采用报告时，Cedar 从 6 提升到 9，Blackridge 从 5 提升到 7。这是对一种明确打法的检验。

## 复核

本目录的 `scenarios_v10.json` 是两张新图的验证器输入。将它与教师包中原样的 `sim_v10.py` 和 `verify_v10.py` 放进同一个新目录，在该目录执行 `python3 verify_v10.py` 即可重跑全部关卡验收。原始运行输出见 [instructor-results.txt](instructor-results.txt)。

在本项目根目录运行以下命令。第二条将参数替换为教师交付包的实际位置。

```sh
dotnet run -c Release --project Tools/CLSR.Offline -- test
python3 Tools/MapBalance/observation_checks.py "/path/to/instructor/package"
```

引擎测试从 Unity 实际加载的场景资源读取人数、路费和预算，核对两个最优分数及单队、限额降低的结果，并逐点检查不同投入下的结算和已公开信息。其他策略结果见 [离线基准](../CLSR.Offline/results/benchmark.md)。
